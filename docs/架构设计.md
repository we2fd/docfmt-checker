# 架构设计

> 本文说明「格致 · DocFmtChecker」的分层结构、模块职责、关键数据流，
> 以及几个**有取舍的技术决策**（答辩时这些都是可以展开讲的点）。

---

## 一、整体分层

```
┌──────────────────────────────────────────────────────────────┐
  表现层  frontend/                                           
  index.html（Vue 3 in-DOM 模板）+ Element Plus + 自研样式    
  职责：交互、渲染、定位高亮、雷达图；不含任何格式判定逻辑    
└───────────────────────────┬──────────────────────────────────┘
                            │  REST / JSON（/api/v1）
┌───────────────────────────▼──────────────────────────────────┐
  接口层  backend/app/api/                                    
  system.py    健康 / 配置 / 统计                             
  documents.py 上传 / 检查 / 修复 / 导出                      
  rules.py     规则集读改启停（含「快速调整」阈值）           
  templates.py 参考模板校准（上传 / 推导 / 应用）             
  职责：参数校验、HTTP 语义、异常 → 错误码映射                
└───────────────────────────┬──────────────────────────────────┘
┌───────────────────────────▼──────────────────────────────────┐
  服务层  backend/app/services.py  ——  DocFmtService          
  职责：业务流程编排（上传→查重→检查→修复→导出→校准）         
        以及文档模型与参考模板的内存缓存                      
└───────────────────────────┬──────────────────────────────────┘
┌───────────────────────────▼──────────────────────────────────┐
  核心引擎  core/  ★ 不依赖 FastAPI，可纯 CLI 调用            
  ① docmodel   文档解析 + 格式取值链                          
  ② rules      规则模型 + 16 个检查器登记表                   
  ③ engine     检查 + 四维度评分                              
  ④ fixer      保守修复（4 个动作）                           
  ⑤ report     报告生成（Markdown / HTML）                    
  ⑥ template   阈值反推 + 快速调整分组（量模板、出建议）      
└───────────────────────────┬──────────────────────────────────┘
┌───────────────────────────▼──────────────────────────────────┐
  持久层  db.py + data/                                       
  SQLite：documents / fixed_files / rulesets                  
  文件：uploads/（待检） fixed/（修复） templates/（模板）    
└──────────────────────────────────────────────────────────────┘
```

**关键约束：`core/` 不允许 import 任何 Web 框架。**
这样核心引擎可以被单元测试直接实例化，也能被将来的命令行版本、批处理脚本复用。
`tests/test_engine.py` 就是这么写的——直接 `parse_docx()` + `run_checks()`，不经网络。

## 二、模块职责

### ① `core/docmodel.py` —— 文档解析与格式取值链

**输入**：`.docx` 路径　**输出**：`DocumentModel`

```python
DocumentModel
├─ paragraphs: list[ParagraphInfo]     # 段落（含表格内段落）
├─ sections:   list[SectionInfo]       # 节：纸张、页边距、页眉页脚
├─ tables / figure_captions / table_captions
├─ headings: list[ParagraphInfo]       # 仅 kind == "heading"
├─ title / abstract / keywords / references
└─ stats: 段落数 / 字数 / 标题数 ...
```

`ParagraphInfo` 里，每个属性不是裸值，而是 `Value`：

```python
class Value:
    value: Any            # 生效值
    source: str           # missing | docDefault | style | direct
    style_id: str | None  # 若来自样式，记下是哪个样式
```

**取值链解析（`StyleResolver`）** —— 本项目最核心的一段逻辑。Word 的格式继承顺序是：

```
docDefaults（文档默认）  <  基础样式  <  派生样式（basedOn 链）  <  直接格式
```

`paragraph_levels()` / `run_levels()` 返回一个**自底向上的候选层列表**，
`chain()` 负责沿 `basedOn` 向上回溯（带**环保护**，避免样式表里出现
`A basedOn B, B basedOn A` 这种畸形数据导致死循环）。

于是「宋体小四」这件事被拆成了两种截然不同的诊断结论：

| 场景 | 报告措辞 | 整改动作 |
| --- | --- | --- |
| 字号 12pt，来源 = 样式「正文」 | 与规范一致 | 无需处理 |
| 字号 14pt，来源 = **直接格式** | 实际 14pt（段落/文字直接格式） | 建议清除直接格式，让样式生效 |
| 字号缺失 | 未能识别（需人工确认） | 标记为待确认，**不扣分** |

> 只报"实际值"是没有指导意义的——用户不知道去改样式、改文档默认值，还是改这一段。

**其他解析要点**

- **表格内段落**也要解析，并打上 `in_table=True`，避免规则把表格文字当正文误判。
- **标题识别**：优先看 Word 的 `w:outlineLvl` / 标题样式；`headings` 只收录
  `kind == "heading"` 的段落，避免把"摘要""关键词"这类结构性段落计入标题。
- **页码检测**：除了扫每个 section 的页脚 XML，还有一层兜底
  （`_document_footer_has_page`），防止"页码设在默认页脚、被某个节的设置覆盖"这类漏检。

### ② `core/rules.py` —— 规则模型与检查器登记表

三样东西：

1. **`Rule` / `Ruleset`**：规则的数据模型（id、name、category、severity、checker、params、suggestion、reference）。
2. **`CHECKERS`**：16 个检查器的登记表，每条声明它**必须提供哪些参数**
   （如 `prop_equals` 需要 `prop` + `expected`）。解析规则集时据此校验，
   缺参数、参数名写错都会立刻报错。
3. **`parse_ruleset` / `dump_ruleset`**：YAML ↔ 对象互转，**错误提示必须可操作**。

第 3 点是刻意强化的：法解析规则集时，报错不能只说"格式错误"，而要给出
「哪一条、哪个字段、期望什么、可用值有哪些」。例如：

```text
layout.page.width：未知的 checker「prop_equals2」，可用值见规则设计文档。
layout.margin.top：缺少必填参数「expected」。
```

界面上编辑 YAML 时，这类错误会直接显示在教学式提示里——因为**规则集是给老师改的**，
错误提示的质量直接决定了这个功能能不能用。

### ③ `core/engine.py` —— 检查引擎与评分

```python
run_checks(doc, ruleset) -> {
    "issues": [Issue],            # 问题清单
    "rule_results": [RuleResult], # 56 条规则各自的判定结果
    "score": {...},               # 四维度分 + 总分 + 等级
    "summary": {...}
}
```

**执行流程**：对每条启用的规则 → 按 `checker` 名字取出对应函数 →
传入 `(doc, rule, sections)` → 返回 `(fail_count, issues)`。

16 个检查函数是按"判定方式"划分的，不是按"业务规则"划分的：

| 类别 | 检查器 | 说明 |
| --- | --- | --- |
| 属性比较 | `prop_equals` `prop_range` `prop_in_set` | 单值 / 区间 / 枚举 |
| 全篇一致性 | `consistency` | 同类对象该属性必须全篇一致（取多数派） |
| 结构 | `heading_no_skip` `heading_style_used` `empty_heading` `required_section` | 标题层级、样式、章节完备性 |
| 图表 | `numbering_continuous` `caption_referenced` | 编号连续、正文引用 |
| 文本 | `punctuation_mix` `reference_format` `length_range` | 标点、著录要素、字数 |
| 段落内 | `paragraph_run_uniform` `blank_line_run` | 同段字号一致、连续空行 |
| 页面 | `page_number_present` | 页脚页码 |

**评分算法**

```python
CATEGORY_WEIGHTS = {"layout": 0.30, "structure": 0.30,
                    "consistency": 0.20, "content": 0.20}
ERROR_PENALTY_PER_ITEM = 4.0
ERROR_PENALTY_CAP      = 30.0
```

1. **维度分** = 该维度内 `pass / (pass + fail)`，`unknown` 与 `disabled` 进入分子分母之外。
2. **加权总分** = Σ(维度分 × 权重) / Σ(参与计算的权重)。
   若某维度**全部规则都是 unknown**，该维度 `score = None`，
   并从加权分母中剔除——**不能因为它没法判定就拉低总分**。
3. **错误扣分**：每条 `severity == "error"` 的问题再扣 4 分，单次最多扣 30 分。
4. **等级**：A(≥90) / B(≥80) / C(≥70) / D(≥60) / E(<60)。

有两类检查器被显式声明为「空即通过」（`ZERO_IS_PASS`）：

```python
ZERO_IS_PASS = {"paragraph_run_uniform", "blank_line_run"}
```

因为"本次文档中没有连续空行"本身就是**合格**，而不是"无法判定"。
如果不做这个区分，一份完全规范的文档会冒出十几个 `unknown` 项，报告会很难看且失去公信力。

### ④ `core/fixer.py` —— 保守修复

四个动作，按固定顺序执行（顺序会互相影响，不能乱）：

| 动作 | 做什么 | 风险 | 边界处理 |
| --- | --- | --- | --- |
| `blank_lines` | 连续空段落压成 1 个 | 低 | 只删纯空段落 |
| `punctuation` | 中文语句里的半角标点改全角 | 低 | 只处理中文占比高的段落，跳过参考文献与表格 |
| `font_size` | 正文字号统一回"多数派" | 中 | **只改已经显式设置过**且偏离多数派的；不给继承样式的段落新增直接格式 |
| `caption_numbering` | 图表题注重排为连续序号 | 中 | 保留"3-1"式章节前缀，只改数字不动文字 |

实现上的一个坑：python-docx 的 `Run` 对象**没有** `direct_props` 属性，
直接格式信息存在我们自己的 `RunInfo` 模型里。所以改字号时必须
**按索引对齐**——`para.docx_paragraph.runs[position].font.size = Pt(...)`，
其中 `position` 来自 `RunInfo`。写错成 `run.direct_props` 会抛 `AttributeError`。

**永远生成新文件**：`fix()` 产出的文件落到 `data/fixed/`，原文件路径不动，
并记录 `diff_json`（改了哪几处、原文是什么、改成什么）。界面上两栏对比展示。

### ⑤ `core/report.py` —— 报告生成

- `build_markdown()`：整改清单，按维度分组，每条含位置、实际值、期望值、建议。
- `build_html()`：可直接打印的报告，内联样式（**不依赖外部 CSS**，保证另存为单文件也能看）。

两者都接受 `report` 字典 + 文档名 + 生成时间，**纯函数、无副作用**，方便单测。

### ⑥ `core/template.py` —— 阈值反推与快速调整

这是 M6 新增的模块，服务两个功能，但它**本身不含任何"论文格式知识"**——
这正是它最值得讲的地方。

**两个入口**

```python
quick_groups(ruleset)        # 「快速调整」：把可调阈值自动分组
derive_proposals(ruleset, doc)  # 「参考模板校准」：量一份模板，反推每条规则的阈值
```

**为什么能做到零硬编码**

规则自己已经声明了"判哪类对象"（`scope`）、"判哪个属性"（`prop`）、
"考的是数值本身"（`checker` 属于 `MEASURABLE_CHECKERS`）。所以"读模板反推"
这件事可以直接**复用引擎自己的两个原语**：

```python
paras = select(doc, rule.params["scope"])       # 取到"正文"这一类段落
vals  = [get_prop(p, rule.params["prop"]) for p in paras]
```

上层完全不知道 `body` 是什么、`font_size` 是什么。**新增一条阈值型规则，
两个功能自动认识它**——不需要维护任何映射表。

**四条设计约束**

| 约束 | 做法 | 理由 |
| --- | --- | --- |
| 取众数不取平均 | `_dominant()` 取出现次数最多的值 | 模板里"正文"有上百段，平均会被个别异常段拉偏 |
| 每个建议带置信度 | `众数次数 / 有效样本数`，低于 80% 界面标黄 | 让用户知道"这个值有多可信"，而不是照单全收 |
| 无阈值就明说 | 结构类规则标 `not_applicable` | 标题不跳级这类判的是"结构对不对"，没有可量化的阈值 |
| 只推导不自动应用 | `profile` 阶段纯只读，`apply` 才写回 | 规则的改动必须是**用户按下的**，机器不替它做决定 |

**与安全检查的接口**

`validate_patch(rule, patch)` 是唯一允许改规则参数的入口，它做三道守门：

```python
ALLOWED_PATCH_KEYS = {"expected", "tol", "min", "max", "allowed"}
```

1. **键白名单**——只有阈值类参数能改，`scope` / `checker` / `severity` 一律拒绝；
2. **取值域校验**——字号 5~100 磅、页边距 0~10 厘米……越界直接拒；
3. **一致性校验**——`min > max`、负容差、空集合、未知枚举值，逐项给出可读原因。

批量应用时**一条失败不影响其余**：`apply_updates()` 收集 `applied` 与 `rejected`
两份清单返回，界面上一并展示，用户能看清"哪几条进去了、哪几条没进去、为什么"。

> 一个具体的坑：判断"是不是字体名"曾写成 `prop.startswith("font")`，
> 结果把 `font_size` 也匹配上了，`12` 被当成字符串 `"12"`，
> 于是越界校验和容差计算全都在错误的类型上进行。→ 改为**精确匹配**
> `FONT_PROPS` 并用 `is_font_prop()` 统一判断。

## 三、关键数据流

### 上传 → 检查

```
用户拖入 .docx
  → POST /api/v1/documents（multipart）
    → 校验扩展名 / 大小；旧版 .doc 等给出「另存为」的可操作提示
    → 计算 sha256 ──命中──→ 复用已有 doc_id（不重复入库）
    → 落盘 data/uploads/ + 写入 documents 表
  → POST /api/v1/documents/{id}/check
    → DocFmtService 取文档模型（内存缓存，命中就不重新解析）
    → run_checks(doc, ruleset)
    → 报告快照写入 documents.report_json（便于历史回溯与统计）
  → 返回 issues + rule_results + score
```

**查重为什么按 sha256**：答辩现场演示时经常反复载入同一份样例，
没有查重的话文档列表会迅速被重复项淹没。

### 定位到原文

```
前端点「定位到原文」
  → 使用 issue.location.paragraph_index
  → 切到「原文对照」页签，滚动并高亮该段（加 .is-target 类）
```

因此 `_issue()` 里**必须把 `location` 的键全部初始化**
（`paragraph_index` / `section` / `snippet` / `style_name` / `in_table`），
哪怕值是 `None`。否则"页码缺失"这类**没有具体段落**的问题，
前端读取 `location.paragraph_index` 会拿到 `undefined`，定位按钮直接失效。
—— 这个坑是自检阶段实际踩到的，后来改成"所有键一律先置位"。

### 参考模板校准（只读推导 → 用户确认 → 写回）

```
上传学校模板.docx
  → POST /api/v1/templates/profile
    → 落盘 data/templates/{id}__{name}      ← 不进 documents 台账
    → parse_docx() 得到 DocumentModel
    → derive_proposals(ruleset, doc)
        ├─ profile_template()  按角色（题目/标题/正文/摘要/题注/参考文献）汇总格式画像
        └─ derive_one()        逐条规则量模板 → 建议值 + 置信度 + 状态
    → 返回 proposals（★ 全程未改动规则集）
  → 用户在界面勾选
  → POST /api/v1/templates/apply
    → validate_patch() 逐条守门
    → apply_updates() 合并进规则集 + 在 meta.description 留下模板出处
  → 下次 /check 即按新阈值判定
```

三种"派生状态"要分清，这是这个功能诚实的地方：

| 状态 | 含义 | 界面表现 |
| --- | --- | --- |
| `proposed` | 模板实测值与现阈值不同 → 给出建议值 | 默认勾选，附置信度 |
| `unchanged` | 模板实测值与现阈值已一致 | 显示"保持不变"，不可勾 |
| `reference` | 一致性类规则：给出**参考值 + 占比**而非阈值 | 只读展示 |
| `not_applicable` | 结构类规则：**没有可推导的阈值** | 说明原因 |
| `skipped` | 模板里根本没这类对象（如无摘要） | 略过 |

> `not_applicable` 与 `skipped` 是两种不同的"什么都没做"：
> 前者的意思是"这类规则永远推不出阈值"，后者是"这份模板恰好没有这种对象"。
> 混为一谈会让用户误以为换一份模板就能推出结构类规则。

## 四、技术决策与取舍

| 决策 | 选择 | 备选方案 | 理由 |
| --- | --- | --- | --- |
| 规则存放 | **YAML 数据文件** | 硬编码在 Python 里 | 规则数量大、变动频繁；换学校规范不用改代码，也让"规则"成为可交付物 |
| 是否用 ORM | **不用，标准库 sqlite3** | SQLAlchemy | 三张表、查询简单；省一个依赖，答辩时能直接讲 SQL |
| 前端构建 | **无构建（全局构建版 Vue）** | Vite + npm | 免 Node 环境、免 `npm install`、断网可跑；代价是没有 SFC，模板写在一个 HTML 里 |
| 格式判定 | **取值链 + 来源标注** | 只读 `run.font.size` | 只读生效值会导致"改哪儿"说不清，且会误报（继承来的值也是"生效"的） |
| 无法判定 | **`unknown` 且不进分母** | 当作不合格 | 宁可漏报不误报；报告的可信度 > 覆盖率 |
| 修复策略 | **4 种低风险 + 必生成新文件** | 全自动修复 | 直接格式会焊死样式链；覆盖原文件是不可接受的失败模式 |
| 端到端验证 | **真实端口 + 无头 Chrome CDP** | 只用 TestClient | TestClient 走进程内调用，测不出静态资源 404、Vue 挂载失败这类问题 |
| 规则反推 | **复用规则自带的 `scope`/`prop`，零映射表** | 为每条规则写一段反推逻辑 | 映射表等于把"规则判什么"抄第二遍，加一条规则要改两处，迟早不同步 |
| 反推取值 | **取众数 + 标注置信度，且不自动应用** | 取平均 / 直接写回 | 模板本身可能不规范；规则的改动必须是**用户按下的** |
| 可改范围 | **白名单：只允许改阈值类参数** | 放开整个 `params` | 口径（阈值）随学校变，逻辑（`scope`/`checker`）不该被随手改 |

## 五、错误处理设计

`errors.py` 里是一个异常基类 + 若干子类，**每个异常都带三样东西**：

```python
class DocFmtError(Exception):
    code: str            # 机器可读错误码
    http_status: int     # 对应的 HTTP 状态码
    hint: str            # ★ 给用户的、可操作的下一步建议
    detail: dict         # 结构化上下文
```

例如旧版 `.doc` 的处理：

```text
错误：不支持的文件类型
建议：请在 Word / WPS 中打开该文件，选择「另存为」→
      文件类型选「Word 文档 (*.docx)」，再上传转换后的文件。
```

而 404 也不是干巴巴的"Not Found"，而是
「该文档可能已被删除，请在左侧文档列表中重新上传。」

**设计意图**：报错信息是产品的一部分。用户看到"操作失败"只会困惑，
看到"另存为 .docx"就知道该做什么。端到端自检里有 3 项专门断言错误提示文案。

---

## 六、可扩展性

| 想做的事 | 需要改什么 |
| --- | --- |
| 换一套格式规范 | 只改 `backend/rules/default.yaml`（或界面上传新规则集） |
| 按某所学校的模板校准 | 界面上传参考模板 → 勾选建议 → 应用；**代码零改动**，且**新加的规则也会被自动覆盖** |
| 新增一条同类规则 | 在 YAML 里加一条，复用已有 checker（如再加一个"脚注字号 = 9pt"）；「快速调整」与「参考模板校准」会自动认识它 |
| 新增一类判定方式 | 在 `core/engine.py` 写 `_check_xxx()`，在 `rules.py` 的 `CHECKERS` 里登记 |
| 支持 `.docx` 以外的格式 | 在 `core/docmodel.py` 加一个解析器，产出同样的 `DocumentModel`，上层零改动 |
| 做成命令行批处理 | 直接 `from app.core import parse_docx, run_checks`，不需要 Web 层 |

最后一条是这个分层最实际的收益：**核心引擎不依赖 Web 框架**，
所以"批量扫描一个目录下所有论文"这种需求，五十行脚本就能实现。
