# 规则设计

> 本项目把「毕业论文格式规范」写成了一个 **YAML 数据文件**（`backend/rules/default.yaml`）。
> 引擎只提供 16 种「判定方式」（检查器），完全不知道"论文要求 A4 纸"这类具体规则。
> **换一套规范 = 换一份 YAML，代码零改动。**

---

## 一、规则集文件结构

```yaml
meta:
  id: default
  name: 本科毕业论文格式规范（通用版）
  version: "1.0"
  description: 覆盖排版、结构、一致性、内容四个维度，共 56 条规则。……

rules:
  - id: layout.page.width          # 唯一标识，建议 "维度.对象.属性"
    name: 纸张宽度（A4）            # 报告里显示的中文名称
    category: layout               # layout | structure | consistency | content
    severity: error                # error | warning | info
    checker: prop_equals           # 使用哪个检查器
    params:                        # 检查器所需参数
      target: section
      prop: page_width_cm
      expected: 21.0
      tol: 0.2
    suggestion: 布局 → 页面设置 → 纸张大小选 A4（21 × 29.7 厘米）
    reference: 《本科毕业论文撰写规范》纸张要求   # 规则的出处，可选但建议写
```

### 字段说明

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | ✅ | 全局唯一。修改规则集时靠它做"这条规则有没有被改过"的比对 |
| `name` | ✅ | 界面与报告中的显示名 |
| `category` | ✅ | 决定它进哪个维度、占多少权重 |
| `severity` | ✅ | 决定问题级别与是否触发额外扣分 |
| `checker` | ✅ | 必须是登记表里的 16 个之一 |
| `params` | 视检查器 | 缺必填参数会在解析阶段直接报错 |
| `suggestion` | ✅ | **整改建议**——这是报告里最有价值的一列 |
| `reference` | 可选 | 规范出处；写上去能让报告显得"有依据" |

### 三个维度之外：`severity` 的用法

| severity | 含义 | 对评分的影响 |
| --- | --- | --- |
| `error` | 硬性要求，违反即扣分 | 该规则计入维度分，**且每条问题额外扣 4 分（单次上限 30 分）** |
| `warning` | 应当满足，但不算致命 | 只影响维度分 |
| `info` | 风格建议，供参考 | 只影响维度分 |

> 刻意把 `error` 控制在 12 条（占比 21%），且全部是"纸张、页边距、正文字体字号、
> 章节缺失"这类**一旦错就必须改**的硬项。若把字号一致性这类也标成 `error`，
> 一份只是略有瑕疵的论文会被扣到不及格，报告就失真了。

## 二、16 个检查器

检查器是"判定方式"，按**怎么判**而非**判什么**来划分。

### 属性比较类

| 检查器 | 必填参数 | 判定逻辑 |
| --- | --- | --- |
| `prop_equals` | `prop` `expected` | 生效值必须等于期望值；支持 `tol` 容差（浮点比较） |
| `prop_range` | `prop` `min` `max` | 生效值须落在闭区间内 |
| `prop_in_set` | `prop` `allowed` | 生效值须属于允许集合（如字体 ∈ {宋体, 仿宋, 楷体}） |

这三个都支持 `scope`（作用于哪类段落，如 `body` / `heading1` / `caption`）
与 `kind_prop` / `kind_value`（行距要先判断是"倍数"还是"固定值"，两种量纲不能一起比）。

### 一致性类

| 检查器 | 必填参数 | 判定逻辑 |
| --- | --- | --- |
| `consistency` | `prop` | 同类对象的该属性必须全篇一致；以**多数派**为准，报出少数派所在位置 |

> **为什么取"多数派"而不是"第一个"**：如果文档第一个标题恰好是错的，
> 拿它当基准会导致其余 20 个正确标题全被报为问题。取多数派符合直觉——
> 「大家都这样、就你不一样」才是异常。

### 结构类

| 检查器 | 必填参数 | 判定逻辑 |
| --- | --- | --- |
| `heading_no_skip` | — | 标题层级不得跳级（出现三级标题前必须已有二级） |
| `heading_style_used` | — | 标题应使用 Word 内置标题样式（否则无法生成目录） |
| `empty_heading` | — | 标题下面必须有正文，不能出现光杆标题 |
| `required_section` | `names` | 必须包含指定章节（按名称模糊匹配） |

### 图表类

| 检查器 | 必填参数 | 判定逻辑 |
| --- | --- | --- |
| `numbering_continuous` | `prefix` | 如"图 1 / 图 2 / 图 4"→ 缺图 3；支持"3-1"式章节前缀 |
| `caption_referenced` | — | 图表编号应在正文被引用（"如图 3-1 所示"） |

### 文本类

| 检查器 | 必填参数 | 判定逻辑 |
| --- | --- | --- |
| `punctuation_mix` | — | 中文语境不得混用英文半角标点 |
| `reference_format` | — | 参考文献条目应含基本著录要素（作者、题名、出处） |
| `length_range` | `min` `max` | 字数 / 条目数 / 关键词个数须落在区间内 |

### 段落级

| 检查器 | 必填参数 | 判定逻辑 |
| --- | --- | --- |
| `paragraph_run_uniform` | — | 同一段落内的字号/字体必须一致（防"一个词单独变大"） |
| `blank_line_run` | `max_consecutive` | 连续空段落数不得超过阈值 |

### 页面

| 检查器 | 必填参数 | 判定逻辑 |
| --- | --- | --- |
| `page_number_present` | — | 页脚应有页码（含默认页脚兜底检测） |

## 四、判定结果的三种状态

每条规则对同一份文档的判定，最终落在三种状态上：

| 状态 | 含义 | 是否进评分分母 |
| --- | --- | --- |
| `pass` | 通过 | ✅ 进 |
| `fail` | 未通过，产出问题 | ✅ 进 |
| `unknown` | **本次文档中没有可判定的对象** | ❌ **不进** |
| `disabled` | 被用户在界面上停用 | ❌ 不进 |

`unknown` 是"宁可漏报不误报"的关键落地。举例：规则
「`content.reference.format` 参考文献著录要素完整」，
若这篇论文压根没有参考文献章节，那么：

- 如果按 `fail` 处理 → 白白扣分，用户觉得莫名其妙；
- 如果按 `pass` 处理 → 掩盖了"缺参考文献"这个真问题（不过它会被
  `structure.references.required` 这条单独的规则抓到）；
- 正确做法 → 标为 `unknown`，在报告里归入「**待人工确认**」，**且不计入分母**。

### 例外：有两类检查器「空即通过」

```python
ZERO_IS_PASS = {"paragraph_run_uniform", "blank_line_run"}
```

「段落内格式统一」和「无连续空行」这两条，**"文档里没有相关对象"本身就是合格**，
不是"无法判定"。如果也标成 `unknown`，一份干净的论文会冒出十几个"待人工确认"，
报告看起来像有问题，反而损害可信度。

## 五、评分算法

```python
CATEGORY_WEIGHTS = {"layout": 0.30, "structure": 0.30,
                    "consistency": 0.20, "content": 0.20}
ERROR_PENALTY_PER_ITEM = 4.0     # 每条 error 额外扣分
ERROR_PENALTY_CAP      = 30.0    # 扣分上限
```

```
维度分 = pass / (pass + fail)                      # unknown 与 disabled 不参与
总分   = Σ(维度分 × 权重) / Σ(参与计算的权重)        # 全 unknown 的维度整条剔除
最终分 = max(0, 总分 − min(30, error 条数 × 4))
等级   = A≥90 / B≥80 / C≥70 / D≥60 / E<60
```

**为什么排版与结构权重最高（各 30%）**：这两项是"硬性合规"，
不合规意味着论文不符合提交格式；一致性与内容（各 20%）更偏"质量观感"。

**为什么是全 unknown 的维度剔除而不是记 0 分**：
一篇纯外文论文可能没有任何中文标点问题，若把该维度记 0 分，
总分会被无理由拉低 20%。剔除后各维度权重重新归一化，评分才公平。

### 实测校准结果

| 样例 | 得分 | 等级 | 说明 |
| --- | --- | --- | --- |
| `01-规范样本.docx` | **100** | A | 完全符合规范，**零误报** |
| `02-排版问题样本.docx` | 46 | E | 排版问题密集（40 条） |
| `03-结构问题样本.docx` | 71 | C | 缺关键词 + 图表跳号 + 标题跳级 |
| `04-一致性与标点样本.docx` | 66 | D | 同段字号不一 + 中西标点混用 |

> 02 号样本刻意做得"很糟"，用来验证引擎的检出能力；01 号样本用来验证**不误报**——
> 后者其实更难，也是整个设计的核心约束。

## 六、如何新增一条规则

**场景**：学校要求"脚注字号必须为小五（9pt）"。

如果已有检查器能覆盖，**只改 YAML，不动代码**：

```yaml
  - id: layout.footnote.size
    name: 脚注字号
    category: layout
    severity: info
    checker: prop_equals
    params:
      scope: footnote        # 若引擎已支持该 scope
      prop: font_size
      expected: 9
      tol: 0.5
    suggestion: 选中脚注文字 → 开始 → 字体 → 字号选「小五」
    reference: 《本科毕业论文撰写规范》脚注要求
```

若需要**全新的判定方式**（例如"检查公式编号是否右对齐"），则需两步：

1. 在 `core/engine.py` 新增 `_check_formula_numbering(doc, rule, sections)`，
   返回 `(fail_count, issues)`；
2. 在 `core/rules.py` 的 `CHECKERS` 里登记：

```python
"formula_numbering": {"summary": "公式编号应右对齐", "required": ["prefix"]},
```

然后就能在 YAML 里用 `checker: formula_numbering` 了。

> **新增检查器属于"扩展引擎能力"**，不再是纯数据改动。
> 但在 56 条规则里，绝大多数格式要求都能被现有 16 个检查器覆盖——
> 这正是"按判定方式划分检查器"带来的复用力。

**新加的规则会自动出现在「快速调整」和「参考模板校准」里**，不需要额外登记：

- 「快速调整」按 **checker + params 的形状**自动判断，只要新规则用的是
  `prop_equals` / `prop_range` / `prop_in_set` 这三个阈值型检查器，
  就会被自动摊成表单卡片，并自动配上单位与取值范围；
- 「参考模板校准」按规则自己声明的 `scope` / `prop` / `target` 去量模板，
  同样不需要任何映射表。

也就是说，**上面那条 YAML 一加上，两个新功能立刻认识它**——这是"规则自带
元信息"（规则说自己判什么、判哪个对象、阈值在哪）带来的直接好处。

## 七、规则集的编辑方式

规则集的调整分两条路：**直接编辑数据**（明确、可版本化）与
**在界面上改**（快速、不需要懂 YAML）。后者又分两种粒度：

| 方式 | 适用场景 | 需要懂 YAML 吗 |
| --- | --- | --- |
| 直接改 `backend/rules/default.yaml` | 开发期、需要提交到版本库 | ✅ |
| 界面「规则集 → YAML 原文」直接编辑并保存 | 批量调整、改 `scope`/`checker` 等结构字段 | ✅ |
| 界面「规则集 → 可视化配置」逐条启停 | 答辩演示、临时试算 | ❌ |
| 界面「规则集 → **快速调整**」改阈值 | 只改字号/行距/页边距/字数区间这类数字 | ❌ |
| 界面「规则集 → **参考模板校准**」 | 手上有学校模板，想按模板反推 | ❌ |
| 接口 `PUT /api/v1/rules/{id}` | 脚本化批量处理 | — |
| 界面「一键恢复内置默认」 | 演示前复位，避免忘记改过什么 | ❌ |

> 「可视化配置」改的是**某条规则启不启用**，「快速调整」改的是**某条规则的阈值**——
> 两者互补，都在同一个「规则集」页签下。

编辑 YAML 时若语法有误，界面会给出**教学式错误**，例如：

```text
YAML 语法错误：mapping values are not allowed here
  in "<unicode string>", line 4, column 12:
        name: 坏: 值
               ^
```

这个 `^` 指向错误列号的提示，是 YAML 库原生给的——直接透传比自作聪明地改写成
"格式错误"有用得多。

> **写 YAML 的一个坑**：值里含"冒号 + 空格"（如 `年份: 页码`）必须加引号，
> 否则会被解析成嵌套映射。内置规则集里就有一处因此加上了双引号。

## 八、快速调整：不改 YAML 也能改阈值

「快速调整」做的事很简单——**把规则集里所有"靠数字判定"的参数摊成一张表单**。

### 哪些规则会被列出来

只有声明了可量化阈值的检查器才进这张表：

```python
MEASURABLE_CHECKERS = ("prop_equals", "prop_range", "prop_in_set")
```

其余检查器（`consistency`、结构类、文本类、段落类、页面类）判定的是
"是否一致 / 有没有 / 结不结构对"，**没有单个可调的阈值**，因此不出现在这里
（它们仍可在「可视化配置」里启停，或在 YAML 页签里改）。

内置规则集里共有 **30 项可调阈值，自动分成 10 组**（按"维度 → 对象"聚合，
如「排版 · 页面 / 排版 · 正文 / 排版 · 标题 / 结构 · 字数」）。

### 每张卡片上的三样东西都是自动推出来的

| 卡片元素 | 从哪来 |
| --- | --- |
| **单位**（磅 / 厘米 / 倍 / 字 / 条） | 按 `prop` 查表：`font_size` → 磅，`page_width_cm` → 厘米，`line_spacing` → 倍…… |
| **合理上下限** | 按 `prop` 查表：字号 5~100 磅、页边距 0~10 厘米、行距倍数 1.0~5.0…… |
| **步进**（上下箭头一次动多少） | 按 `prop` 查表：字号 0.5、页边距 0.05…… |

**为什么要给上下限**：阈值一旦被改成离谱的值（比如字号设成 9999），
规则就永远判不合格，用户却不知道是自己填错了。所以越界值在**服务端**就被拦下：

```text
规则「正文字号」的取值 9999.0 超出合理范围（5.0 ~ 100.0）。
```

### 只能改阈值，不能改结构

允许被改的键只有五个：

```python
ALLOWED_PATCH_KEYS = {"expected", "tol", "min", "max", "allowed"}
```

试图在「快速调整」里改 `scope`（作用对象）、`checker`（判定方式）、`severity`
这类**结构字段**，会被明确拒绝并指路：

```text
规则「正文字号」不支持在这里修改参数：scope。
（如需修改判定方式/作用对象，请到「YAML 原文」页签。）
```

这样划分的用意：**阈值是"口径"，结构是"逻辑"**。口径随学校变，逻辑不该被随手改。

## 九、参考模板校准：把学校模板读成规则

这是本项目里**最能体现"规则即数据"价值**的一个功能——因为它的实现里
**没有一行硬编码的映射表**。

### 为什么可以零硬编码

规则自己已经声明了三件事：

```yaml
- id: layout.body.size
  checker: prop_equals
  params:
    scope: body        # ← 判哪类对象
    prop: font_size    # ← 判哪个属性
    expected: 12       # ← 考的是"数值本身是多少"
```

于是"读一份模板并反推阈值"这件事，可以完全**复用引擎自己的两个原语**：

```python
paras = select(doc, rule.params["scope"])          # 取到"正文"这一类段落
vals  = [get_prop(p, rule.params["prop"])          # 量出每段该属性的实际值
         for p in paras]
```

再把这批实测值汇总成一个建议阈值——**不需要知道"body"是什么、`font_size` 是什么**。
所以**新增一条阈值型规则，模板校准功能自动认识它**。

### 四条设计约束

**① 取众数，不取平均**

一份模板里"正文"段落少则几十、多则上百个。取平均值会被个别异常段落拉偏
（比如模板里混进了两段 10.5 磅的表格说明）；取**众数**才代表"这份模板真正长什么样"。

**② 每个建议都带置信度**

置信度 = `众数出现次数 / 有效样本数`。低于 80% 的在界面上**标黄**，提示人工复核：

```text
正文字号   实测 14 磅   置信度 62%   ⚠ 建议复核
```

**③ 结构类规则明确说"没有可推导的阈值"**

`heading_no_skip`（标题不跳级）、`numbering_continuous`（图表编号连续）、
`required_section`（必须含摘要）这些规则，判定的是"有没有 / 结构对不对"，
**不存在一个可以从模板里读出来的数字**。这时界面直说"没有可推导的阈值"，
而不是硬凑一个出来。

> 这跟第四节的 `unknown` 是同一种克制的、贯穿全项目的态度：
> **不会就是不会，不装。**

**④ 只推导，不自动应用**

上传模板后的第一遍是**纯只读**的：量格式、出建议，**一个字节都不改规则集**。
用户逐条勾选、点「应用」之后才写回；写回时还会在规则集说明里留下出处：

```text
……（阈值已按参考模板「XX大学本科毕业论文模板.docx」校准 · 2026-09-18）
```

这样下次有人问"你们这套阈值哪来的"，规则集自己就能回答。

### 完整流程

```text
选择参考模板.docx
  → POST /templates/profile     量格式 + 出建议（只读，规则集不变）
  → 界面「格式画像表」：题目 / 各级标题 / 正文 / 摘要 / 关键词 / 题注 / 参考文献
  → 界面「逐条建议表」：勾选框 + 实测值 + 置信度 + 建议值
  → 用户勾选
  → POST /templates/apply       写回规则集 + 记出处
  → 回到体检页重新检查即生效
```

> 参考模板单独存放在 `data/templates/`，**不会混进"待检查文档"列表**——
> 它是一把尺子，不是一份待体检的论文。
